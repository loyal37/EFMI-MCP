# EFMI MCP — working agreement

- When resuming work, read `.ai-memory/CURRENT_STATE.md` and `.ai-memory/TASKS.md` first; architecture, constraints and earlier decisions are in the other memory documents.
- Modify only this project, `F:\EFMI MCP`. The EFMI/XXMI installation, the launcher configuration, `d3d11.dll`, `d3dx.ini`, `Core` and existing mods are read-only; the sandbox uses private copies inside this project. The one exception: when `efmi_verify_exported_mod` deploys a test mod exported by this tool, it writes, updates or deletes only the files it recorded, inside a dedicated folder under `<EFMI>\Mods` that this tool created and marked with `efmi-mcp-deployment.json`; other mods are not moved or disabled. A mod of the user's may be disabled temporarily (renamed to `DISABLED_…`) only when the user explicitly asks for it on the spot; it is renamed back afterwards and the result says so. Likewise, a file of one of the user's mods may be modified only when the user names that mod on the spot (on 2026-10-08 the user asked for the INI of `TangTang Seaside Breeze 1.4` to be changed from RabbitFX to slots): first leave a backup in the same folder that XXMI will not load (a file name that does not end in `.ini`), and state the scope of the change and the location of the backup in the result; such a request covers only the mod that was named.
- The user has authorized the tool to run the normal F10 reload flow; `efmi_reload_and_capture` does not edit original files directly, but XXMI itself may save persistent variables. Input sent, new frame captured, and target mod verified must be reported separately; `reload_requested` must not be treated as a receipt that the reload completed, and F10 must not be resent automatically. The user also asked (2026-10-07) that the agent may switch all mods off or on at any time with EFMI's own F11 (`efmi_toggle_mods`), to compare the original draws with the mods' draws: the on/off state is taken from EFMI's own notification and reported as unknown when it cannot be read; mods are switched back on when the comparison is done, and a failed key press is not retried.
- Before ending a round of work, update the current state, the tasks and the session log; when there is a new decision or problem, update the corresponding document as well. Record evidence, the scope of verification and what remains; avoid pasting long logs.
- Keep "injection succeeded", "connection succeeded", "data captured" and "verified on a real character" strictly apart; historical sandbox results must not stand in for verification in this round or in the real game.
- After changing the probe, build it and run the relevant regressions. The DLL stays loaded in the process until it exits; a successful build on disk does not mean the running game has loaded the new version, and the user's game is not to be ended without being asked.
- The user's requirement (updated 2026-10-06): after every code change that has passed its verification, review the diff, sync the project memory, create a Git commit unprompted, and push it to `https://github.com/loyal37/EFMI-MCP`. The earlier "no automatic push" agreement is superseded by this explicit request; captures, game assets and ignored build output are not pushed, and remote history is not force-overwritten. The plan document (`docs/model-extraction-export-plan.md`) stays local only, never committed or pushed (the user made this explicit again on 2026-10-07); versions that had already entered old commits are kept, by the user's decision of the same day, and history is not rewritten for this; anything meant for outside readers goes into the README.
- The model workflow is built on integrating LoyalTools: call its entry points (by default the add-on installed in Blender) and do not copy its algorithms; a LoyalTools update should not require changes to this project. New checks rely only on the output files and on XXMI's INI syntax, not on the add-on's naming or the wording of its log. Components posed on the CPU are never modified, following the user's practice (they are deleted in the project and drawn by the game itself): such a component having no entry point, no LOD entry, or being marked "left to the game" is not a problem (user, 2026-10-07).
- Windows opened during tests (the sandbox program and the like) go on the secondary screen and do not take the focus (user, 2026-10-08). The sandbox program does this by default; only `--primary-screen` brings it back to the primary screen. New tests that open a window follow the same rule.
- Everything in this repository is written in English: documents, project memory, code comments, test data and commit messages (user, 2026-10-11). A string that has to match text which another tool produces in a different script is spelled with `\u` escapes.
