# EFMI MCP — Architecture

## Data path

`agent → Python MCP stdio → named pipe → efmi_probe.dll → system D3D11/DXGI objects → capture/read-back → MCP result or exported file`

The probe lives in the game process next to XXMI. `bootstrap.cpp` redirects, in memory, the device-creation export entries of the system D3D11 module and so obtains the real device; `hooks.cpp` replaces the vtable pointers of the real COM objects. The original XXMI DLL files and modules are not a target of modification.

## Probe modules

| File | Responsibility |
| --- | --- |
| `probe/src/dllmain.cpp` | Loads logging, configuration, registry, capture, bootstrap, IPC; pins the DLL until the process exits |
| `probe/src/bootstrap.cpp` | Finds the system runtime, intercepts device creation, resolves the real device / immediate context |
| `probe/src/hooks.cpp` / `hooks.h` | Device/context/swap chain hooks, the Present frame boundary, tracking of draws and resource writes |
| `probe/src/registry.cpp` / `registry.h` | Registration of resources/shaders/input layouts, creation hashes, buffer write history |
| `probe/src/capture.cpp` / `capture.h` | Single-frame and continuous capture, pipeline binding snapshots, GPU data read-back, summaries |
| `probe/src/hash.cpp` / `hash.h` | Computation of XXMI-compatible hashes |
| `probe/src/ipc.cpp` | Named pipe server and request dispatch |
| `probe/src/slotcache.cpp` / `slotcache.h` | Slot cache (0.1.7): settings, folder per game version, writer thread for records and shader bytecode |
| `probe/src/util.cpp` / `common.h` | Logging, configuration, module information, shared declarations |

Device, immediate context and swap chain must belong to the same render target; draw records are filtered by the selected context, and Present decides the frame boundary of a capture. In `0.1.1`, `hooks_attach_device` separates installing hooks from choosing the capture target: hooks are set up for the device first, the first swap chain found binds the corresponding target through `GetDevice` / `GetImmediateContext` and holds references to device and context; an auxiliary device does not override a target that has been chosen. The `context1` capability is stored per context, and GPU writer tracking is also limited to the selected context and requires a swap chain to exist.

Once a target is chosen, a replacement swap chain created by another device is refused, and the log says to restart; deciding automatically which of several swap chains is the main picture is not supported at present. While a swap chain of the same device is destroyed and re-created, the integrity of a capture that crosses that boundary is still to be verified.

`ipc.cpp` / the MCP status return the capture target pointers and the draw count of the selected context; an empty capture shows a warning. Captures in continuous mode carry a generation; after a stop, a restart or a client reconnect, in-flight frames of an old generation must not be published into the new session. This fix has passed the `83` self-test checks and the final full regression.

Server 0.1.14 adds `Session.shader_listing`: a per-connection LRU of bytecode, disassembly and parsed SM4/5.0 SRV references, shared by `efmi_get_texture_slots` and `efmi_get_shader` (128 entries / 32 MiB listing budget). Reconnecting clears the shader cache; bindings are always resolved from the requested capture and are not cached across frames. Slot results distinguish instruction references, declaration-only slots and leftover bindings; failures leave usage unknown. Queries do not read texture payloads or write files. Full shader export is explicit with `save=true`; the probe and protocol are unchanged. See D-023.

A pipe message is `[u32 header_len][u32 payload_len][header JSON][payload]`. The server keeps the records of the last six captures and the bytes of CB / indirect-argument snapshots it has fetched, but the probe only guarantees that the ordinary resources of the latest capture can still be read. An ordinary read returns the content at the time of reading; for the CB as it was at the draw, use `cb_data=true`.

On import, `hashes.py` tries to load `dist/efmi_crc32c.dll` by absolute path and accelerates CRC once the CPU SSE4.2 check and known vectors pass; when the library is missing or unsupported it keeps the Python fallback. Sources and build are in `server/native/`, completely independent of the injected probe. `decode.texture_to_pngs` produces the full PNG and the preview from one decode; compression level 1 keeps the pixels.

### Probe 0.1.7: slot cache

- `cap_on_frame_boundary` starts a "slots" recording when nothing else is recorded, fewer than 4 frames are finishing and `slot_due(frame)`; an explicit capture and the continuous stream take precedence. `cap_on_draw` hands such a frame to `slot_record`, which queries the input layout (skinned filter, cached per layout), index buffer, VS/PS and checks `g_slot_seen` (render thread only; cleared when `slot_generation()` changes or it grows past 200,000). New draws get a `DrawRec` with the IB region (read back and hashed like a capture), the VS/PS SRVs and RTV/DSV views, and the caller via `caller_from_probe` (`g_caller_late` suppresses the per-draw stack walk in the hook).
- `complete_capture` passes such a frame to `slot_push`, which writes one JSON record per draw and calls `slot_submit`; draws whose region was skipped or still pending are removed from `g_slot_seen` to be tried again. `slotcache.cpp` works out the version key, opens `draws.jsonl` for appending, loads the keys already there, de-duplicates and saves bytecode through `reg_get_bytecode`, all on its own thread; a change of version in the same place raises the generation, and `slot_set_config` raises it when the folder changes.

### Probe 0.1.6 / server 0.1.12: contents as they were at the call

- Data: `Capture::conts` (`ContSnap`: one version of a buffer, or one subresource of a texture), `tracks` (per resource pointer: the buffer's current version number, the patch table `ContPatch{ver, off, size, chunk, at}`, whether it is sealed / lost; for a texture, the table of "referenced subresources that have not been written yet"), `cchunks` (staging buffers that hold patches, 4 MiB each, a large patch gets its own). Each binding record carries a `cont` (`ib_cont`, `VbBind` / `CbBind` / `ViewBind`), serialized as `cvb` / `ccb` / `csrv` / `cout` and `cib` parallel to `vb` / `cb` / `srv` / `out`; the table itself is `cont`: `[resource, 0, version]` or `[resource, 1, mip, slice]`.
- References: `cap_on_draw` / `record_stage` call `cont_buffer` / `cont_of_view` for every binding (`ct_kinds` in the request decides which kinds); outputs are referenced by `cap_after_draw` after the original call returns (`ct_out_kinds` plus `ct_match` / `ct_out_all` select the calls), and Dispatch takes the same path.
- Copy before write: before letting a call through, the hooks call `cap_before_write` (CPU-side writes and copies, with subresource and byte range), `cap_before_view_write` (clears through a view, GenerateMips), `cap_before_call_writes` (outputs of a draw / Dispatch, taken from `g_om_out` / `g_cs_out`, re-queried from the runtime only when the bindings changed), `cap_before_unknown_writes` (command lists: sets `ct_unknown`). Before Present, `cont_before_present` handles the swap chain's back buffer. All of this is active only under `g_barrier` (a capture is keeping contents); `g_bar` points to that capture.
- Read-back: `read_content` (job type 6). Textures: read the copy if there is one, otherwise stage one in place. Buffers: `start_read_content` picks the patches whose version number is not below the version asked for (newest to oldest) and, when needed, copies the buffer as it is now; `finish_read_content_buffer` applies them in order. `release_content` (type 7) only frees contents. `stage_subresource` is the common entry point for staging one subresource (1D / 2D / 3D, rounding for block compression, resolving multisampled textures first); `read_texture` uses it as well.
- Write list: in the frame for which `g_events` is set, each write hook calls `cap_event` / `cap_event_view`, recording the kind, "before which call", target and source resource, four numbers, and clear values; serialized as `ev`.
- Status: once per frame the render thread writes the number of copies, the bytes and the number of losses of the capture that keeps contents into a few atomics (`cont_publish`); the status command on the pipe thread reads only those and does not touch the capture object.
- Budget and memory: `ct_budget` (bytes); before allocating a large block `memory_allows` looks at free physical memory and the commit charge, and does not copy when less than 2 GiB of headroom is left. Lost items report the reason when read (`k_cont_why`).
- Server side: `slot_data.py` (which part of a buffer a slot exposes, where the bytes come from), `contents.py` (capture options, wording of writes, binding differences between neighbouring calls `bindings_of` / `binding_changes`, the `dump_frame` export), `capture_model.py` (`content()`, `events()`, `content` of each binding, `viewports`), `parity.compare_contents` (byte-for-byte comparison with XXMI's dump).
- Threads: as before, hooks, frame boundary and read-back jobs all run on the thread that uses the immediate context; serialization reads only fields that no longer change once recording has ended (resource / version / subresource of the `cont` table), and status-like fields are given only at read-back.

### Probe 0.1.5 / server 0.1.8: pipeline state and render target copies before and after a draw

- In a full capture `cap_on_draw` records more: `record_fixed_state` (blend / depth-stencil / rasterizer state objects and their dynamic values, scissor rectangles, the values of the first viewport and the total number of viewports), the samplers in `record_stage`, the description of every bound view (`view_desc_id`), and a snapshot of indirect arguments. State objects and views each have a table (`states`, `views`) that draws refer to by index; entries are de-duplicated by content, and addresses are used only to find candidates. The audit of 2026-10-08 corrected the earlier statement "all viewports": the code queries all of them but serialized only the first.
- The `rt` option of a capture request gives a set of `DrawMatch` (draw number, index buffer object and ordinal, index count, start index, VS / PS hash, any shader hash, origin; every field that is set has to agree). For the first `rt_max` draws that match and have a target that can be copied: before the draw, `rt_copy` copies that mip level / slice of the target (optionally limited by `box`) into a newly created staging texture and leaves the view for `cap_after_draw`; the hook, seeing `g_rt_after` after the original function returns, calls it and the second copy is made. The copies live as long as the capture; `read_rt` reads them by ordinal (through the existing read-back job queue, type 4); `release_rt` (type 5), the next capture or a client disconnect frees them.
- Counters: `rt_matched` (draws that matched), `rt_draws` (draws that were copied), `rt_depth_only` (no colour target and depth was not requested), `rt_bytes`, `rt_over_budget`.
- Server side: `Capture.draw()` expands the new keys into `blend` / `depth_stencil` / `rasterizer` / `scissors` / `samplers` / the `view` of each slot / `indirect.args`; when these keys are missing (old probe or light capture) everything is as before.

### Probe 0.1.2 / server 0.1.4: in-process reload key and reload evidence

`probe/src/reload.cpp` implements the pipe command `reload_key`, executed on the IPC thread; the render thread only records the time and sets an event in the Present hook while a key press is in progress (`reload_on_present`). Flow: check the swap chain, XXMI, the two default bindings in d3dx.ini, the window and the key state → take the foreground (`direct`, or `attach_input` when refused) → wait 3 frames → `SendInput` key down and wait until the down state is read → release at the second Present, or at the first Present that comes later than 10 ms → optionally restore the focus. The receipt comes back as `{"ok":true,"result":{...,"code":...}}`; `code!="ok"` is turned into `ReloadInputError` by the server. From 0.1.3 the same procedure (`key_press_run`) also serves the command `mods_key`: it presses F11, the pre-checks are replaced by `[KeyToggleMods]` in `Core\EFMI\KeyBindings.ini` and the F11 bindings without modifiers in `[Hunting]`, the rest is the same.

The `features` list of the status decides which path the server takes (`reload_workflow.py`): with `reload_key` it uses `send_reload_via_probe`, otherwise the old `send_reload_f10`. `reload_evidence()` reads the `cf` of the resources/shaders in the capture and compares it with `frame_at_key_down` of the receipt. The pre-checks, invalidation of old caches, the wait and the new-frame threshold described in the 0.1.3 section are unchanged.

### Server 0.1.3: reload request, input state and the capture workflow (external key path, still used with an old probe)

`efmi_reload_and_capture` is an MCP tool with side effects that must not be assumed idempotent; the probe protocol/DLL stays at 0.1.1. The workflow reads `d3dx.ini` of the current root and accepts only one `reload_config` and one `reload_fixes = no_modifiers VK_F10` in `[Hunting]`, without changing the configuration. It uses the same connected client and checks the pipe PID, the XXMI path and device/context/swap chain; an ordinary single-frame capture must not be in progress, and a live recording is stopped first.

The execution stage clears the old session captures / latest, invalidates `ModCache`, stops live mode and releases held resources. The input module sends one F10 down/up only to the window of that process, held for about 200 ms, and checks focus, modifier keys and the high bit of GetAsyncKeyState. `key_down_sent` keeps whether SendInput accepted the input; `key_down_observed` requires the high bit to be visible at least once while the key is held. If it was not observed, `ReloadInputError("keydown_not_observed")` is raised, the workflow returns a ToolError for the input stage, the release is still attempted in `finally`, capture does not continue and the key is not pressed again. Only when the key threshold is passed does it wait the default 2000 ms and record the barrier; a later non-empty frame must be later than the original frame / the barrier, with the same PID/device before and after, to be published as latest. Live mode stays stopped.

There is no receipt from XXMI that a reload completed; the tool returns `reload_requested` and a `reload_confirmed` that is always false, and does not equate accepted input or a new frame with the INI having parsed successfully. A failed pre-check keeps the old captures; an error after execution clears the old results and reports whether the input was sent or is unknown, and F10 is not retried automatically. `timeout_ms` is passed only to the subsequent probe capture. This server update needs only an MCP restart, no re-injection and no hunting mode; the saving of persistent variables by a normal F10 is a real side effect.

This state threshold comes from the failure in the real game on 2026-10-06: SendInput returned accepted, but during the scan-code diagnosis the asynchronous high bit was never set, and the mod the user had moved out was still being drawn. It recognises the failure; it does not solve the underlying invisibility of the input, nor does it prove that the game thread observed the key. The probe was not changed, no non-public XXMI call was added, and switching to scan codes was not made a production fix; see BUG-004.

## LoyalTools merged-skeleton bridge (2026-10-06)

`scripts/capture_merged_source.py` saves the complete shared geometry / bone pool, the CBs as they were at the draw, the character's material DDS files and the read-back evidence. The probe must confirm that the complete IB/VB resources have not changed since the capture; the XXMI region hash is only an additional check, and the actual geometry range must be computed from the min/max index of the complete IB.

`server/efmi_mcp/loyal_bridge.py` imports the local LoyalTools dynamically and read-only; it does not execute the package entry point that depends on bpy and writes no bytecode into the reference project. It converts a Capture into LoyalTools' native frame model and calls the original character grouping, matrix de-duplication, source selection (including the blacklist for Liino's rocket boots) and workspace writing directly. CB snapshots are already cut to the original first_constant, and first_constant is reset to zero in the bridge. Every draw keeps its own layout, original index range and signed BaseVertex.

The bone SRV of 0.1.1 can only be read late. Static editing mode must use three independent samples and check the actual geometry bytes, the source of the canonical bone groups, the actual weighted merge across components, and the changing effective bone matrices; this is not a pose snapshot of a specified frame. The CLI entry point `scripts/export_merged_workspace.py` writes `workplace` under the target root; `scripts/verify_merged_workspace_blender.py` actually imports with the installed LoyalTools, checks weights / textures / blueprint and saves a new `.blend`. No LOD mapping is generated for what was not captured.

The live archive stores compact JSON and per-stage `durations_ms`; the second identity check does not compute VB hashes, while IB/CB and the complete-buffer validation of the first frame are kept. The offline bridge caches, per sample, whole buffers that passed SHA validation, and lets the original algorithm read memory through the local globals of cloned reader functions, without modifying LoyalTools source files or module globals; sub-mesh results are isolated with a deep copy from later changes such as output naming.

When the validation of an auxiliary sample ends, its whole-buffer cache is cleared at once, and the export's `finally` empties the registered caches; samples keep copies of the actual geometry slices / matrices for the three-sample comparison. `scripts/test_loyal_bridge_performance.py` loads the old bridge from a specified Git revision, exports alternately with the current implementation, compares files, counts source file reads, and verifies the rejection thresholds / NumPy read semantics / cache release; by default it uses the existing `liimo-static-a/b/c` inside the project and writes test output only inside `captures`.
