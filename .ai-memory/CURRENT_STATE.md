## Probe slot cache (probe 0.1.7, 2026-10-18; sandbox verified and installed, not yet loaded by the game)

- Request: the user keeps slot-style texture bindings (`ps-tN = ...`) because RabbitFX costs too much performance, and slots move with game updates (sometimes all by one, sometimes only in some shaders). Texture hashes are ruled out ("slots only"). The goal is a tool for every version that recognises slot changes and repairs the slot bindings of any mod, not only the user's. The user proposed a slot cache that fills itself like a shader cache: record IB hash, index count and slots while characters are switched in the game. This round built the probe part.
- Evidence behind the design (update of 2026-10-15): shaders that did not change are byte-identical; the 11 changed lit/outline shaders keep t0/t1 and move t2 and up by one; TangTang's component 2 lit shader `2d0b12a7...` -> `c459aece0e923e44` moves t2-t10 by one and leaves t11 and up alone. A migration therefore has to be worked out per old/new shader pair from both bytecodes. XXMI's ShaderCache holds only regex-patched shaders and was rebuilt on 10-15 (no pre-update copies), and `d3dx.ini` has `cache_shaders=0` / `export_shaders=0` (read-only for this project), so the probe keeps the bytecode itself.
- Implementation: `probe/src/slotcache.h/.cpp` (settings `[SlotCache]` in `efmi_probe.ini`, the folder per version, a writer thread for all file work), a "slots" kind of capture in `capture.cpp` (one frame in `every`; only indexed draws not seen before, told apart by IB object + creation serial, offset, format, range, base vertex and VS/PS creation serials; skinned-only filter by `BLENDINDICES` in the input layout; at most `max_new` new draws per frame, the rest later; IB region hashed and read back like a capture; VS/PS SRVs, RTV/DSV formats, layout), the probe command `slot_cache` and `slot_cache` in the status (`ipc.cpp`). Records go to `<probe dir>\slot-cache\<label>+<fingerprint>\draws.jsonl`, de-duplicated by a content key (origin, IB region and resource hash, range, base vertex, VS/PS hashes, shape of the slots; no texture hashes); bytecode once per shader in `shaders\<hash>-<type>.bin`. Label: the first version-like string below 1000 in `globalgamemanagers` (an offline scan found `1.6.3`; Unity's own `2021.3.34f5` is skipped); fingerprint: contents of both `index_main.json` plus size/time of `Endfield.exe`, `GameAssembly.dll` and `globalgamemanagers`. The game started on 10-18 left `Persistent\index_main.json` at its 10-17 time, so it is not rewritten at every start.
- Changes after the self-review, before installation: a cut-off last line of `draws.jsonl` is ended before anything is appended; changing `subdir` makes the render thread forget what it saw (the new folder used to stay empty); the stack walk that tells `game` from `xxmi` is done only for recorded draws (`caller_from_probe`, `g_caller_late`) rather than for every draw of a looked-at frame.
- Verification (sandbox only): new `sandbox/slot_cache_test.py`, 65 checks. With XXMI: by default nothing is recorded in the unskinned scene; with `skinned_only=0` every game draw of a full capture has exactly one matching record (IB hash, resource hash, offset, range, instances, layout, slots with kind/size/format/view format, output formats), bytecode files hash to their names, records of XXMI's overlay carry origin `xxmi`. Without XXMI: exact counts, nothing is submitted again in later frames, a second folder with `max_new=1` receives the same records, going back to the first adds nothing, and after a restart everything is recognised and a cut-off line is ended. Full `run_all.py` on the final build 18/18 (parity 69 x 3 with 0 mismatches, self-test 143, contents 73, contents parity 546/0, slot cache 64 at that point, multi-device 96 + 96, MCP 106, unit suites 27/60/56/25/41/33/25). A run on the build before the last change had one failure, "XXMI did not produce a frame analysis dump" (the sandbox's synthesized F24 had no effect); it did not recur. Re-run on the installed DLL: slot cache 65, self-test 143, MCP 106. Cost (sandbox, about 3000 draws per frame, XXMI present): no measurable frame-time difference even when every frame is looked at; 0.13-0.3 ms per looked-at frame by the probe's own timer.
- Found on the way: with `skinned_only=0` XXMI's overlay (notification text from a ring buffer, buffers recreated) gives new draws in most frames and same-content duplicates; Endfield's characters are drawn with `BLENDINDICES` in the layout (capture of 10-15: 104 skinned indexed draws, 89 of them from mods), so the default filter leaves the overlay out.
- Installation: `dist\efmi_probe.dll` is 0.1.7 (SHA256 `6F8A5CD040C62AF5291F7642EF6264E7123129D54A08F24E5AAE4F32D713F195`, 530,432 bytes); 0.1.6 (`FFFA1315...5C1B`) is in `dist\backup-0.1.6\`. The game was not running, so its next start loads 0.1.7 and begins filling `dist\slot-cache\`.
- Not verified: anything in the real game (label and fingerprint from the real files, cost at about 1600 calls per frame, records of real characters with mods on and off). Nothing reads the cache yet; that is step 2 of T-016.

## Read-only assessment of ZZMI compatibility (evening of 2026-10-09; not adapted, nothing injected)

- The user asked whether this MCP can be used for `D:\XXMI-Launcher-Portable-v2.1.6\ZZMI`. Only the installation and this project's code were read; no ZZMI / launcher / game file was changed, and there was no key press, injection or restart. `ZenlessZoneZero.exe` PID **18692** was seen, and `find_probes()` returned nothing, so there was no connection, capture or verification on a real character.
- **Basis for reuse**: the `d3d11.dll` of the local EFMI and ZZMI are both version **1.2.2.0**, length 3,192,832, with the same SHA256 `EA97846AF4610B9AF42BEDDCCD7F22A5E73E85B25669CD4391EA8000962FDD7D`. The probe works through the system D3D11 device-creation entry points and context interfaces and does not check for the Endfield process name; basic draw / buffer / texture / shader / contents / RTV / UAV capture can be expected to be reusable, limited to the D3D11 path; identical DLLs do not allow the inference that it has passed in Zenless Zone Zero. The server can point at ZZMI with the existing `--efmi-root`, but that does not load the probe; the current automatic connection does not filter game processes by this root either.
- **Local configuration**: the target in ZZMI's `d3dx.ini` is `ZenlessZoneZero.exe`, with shader_hash=3dmigoto, texture_hash=0 and **track_region_hashes=0**; the main IB / VB hash of the current server is the CRC of the drawn region, with resource_hash stored separately. So ZZMI's INI hashes and automatic matching need adapting to whole-resource hashes, and EFMI's region hashes cannot simply be written into them. The installation scan entry point was run and reads the Include / exclude rules; it found 0 active mods / 0 referenced hashes in this directory (which cannot verify matching of non-empty mods).
- **Keys**: only the server's read-only configuration pre-check was called, and the two F10 reload bindings pass; no F10 was sent. ZZMI's switch is F6 / `$costume_mods` in `Core\ZZMI\main.ini`, while the existing server and probe check F11 in `Core\EFMI\KeyBindings.ini` only, so the pre-check refuses; this has to be adapted together with reading the state. The upstream ZZMI sources define F6 as well: <https://raw.githubusercontent.com/leotorrez/ZZMI-Package/main/ZZMI/Core/ZZMI/main.ini>.
- **Model workflow**: `model_capture.instance_config` is fixed to VS t0, stride 16 and specific offsets of the instance CB; `loyal_bridge` / `model_workflow` use the EFMI merged-skeleton project and the corresponding LoyalTools entry points, and cannot be taken as a general character / skeleton / LOD / mod export flow for Zenless Zone Zero. Ordinary bindings and raw resource reads should be accepted separately from these advanced functions. In that round the user only asked about compatibility; no rework or installation was started.
- "Region hash" was then explained: a CRC32C over a stretch of bytes of a buffer selected by offset and length, used to tell meshes in a shared large buffer apart; it has nothing to do with a region of the screen. The IB range is determined by the bind offset, first_index, index_count and the index width; for an indexed draw the VB range is estimated by XXMI's rule and cannot be taken as a byte-for-byte verification of the whole mesh. How ZZMI matches hashes and whether raw resources can be read are two questions; turning on its region hashes or modifying code was not asked for.

## The hair outline of Typhoeus: fixed inside the mod at the user's request (2026-10-09 17:27–17:35, real game PID 12176; one F10)

- The user's request after seeing the conclusion of the next section: do not change RabbitFX, change the mod's INI, and put this part of the code into an INI of its own. The target is the mod on screen (`Mods\Typhoeus Luxuria 1.2 alpha`); other mods were not touched.
- **Changes** (all inside that mod's folder): a new `RabbitFX_HairOutlineFix.ini` (namespace `RabbitFXHairOutlineFix`, 1780 bytes); in `Typhoeus.ini` only line 601 changed, where `run = CommandList\RabbitFx\SetTextures` of the hair section became `run = CommandList\RabbitFXHairOutlineFix\SetTextures`; the backup made before the change is `Typhoeus.ini.before-hair-outline-fix-20261009` in the same folder (SHA256 `aa9b585e…`, a file name that does not end in `.ini`). `RabbitFX.ini` and `Typhoeus_Interaction.ini` were not touched. Copies and the diff are in `captures/rabbitfx-hair-outline-20261009/`.
- **Approach**: the new INI gives each of the two wrongly assigned shaders (XXMI original hashes `fadc3687dd18e11c`, `bff61f7703cd52ee`) a `[ShaderOverride]` with its own `filter_index = 2718.1` and `post ps-t72 = null`. The `filter_index` of an explicit section beats the tag a ShaderRegex gives (in the 3DMigoto sources the regex value is used "only when none has been set yet", confirmed here in the real game), so RabbitFX's `SetTextures` (which recognises only `1718.1` / `1718.2`) no longer puts textures into this pass, and the alpha test goes back to the game's own mask. `[CommandListSetTextures]` of the new INI binds `Resource\RabbitFX\Diffuse` to `ps-t72` when `ps == $outline` (that is where the rewritten shader reads the outline colour), clears `ps-t70`, and then calls RabbitFX's `SetTextures` as usual; the other passes go entirely the way RabbitFX had them.
- **Verification in the real game** (one F10, announced beforehand; `reload_confirmed`; frames 398037 / 399679): in the colour pass `ps-t70` is empty and `ps-t72` is the hair diffuse `0409102f`, and in the draw right after it `ps-t72` is already cleared; 5039 of 5100 hull pixels are coloured (99%; 5140 / 825 before the fix, 4642 / 4569 for the original with mods off); the prepass, the other colour variant and the two lit passes still have `t70` bound by RabbitFX as usual; the hair diffuse appears only in the hair's own 6 draws and does not leak into other draws. Comparison picture `head-before-vs-after-fix.png`.
- **Where it affects other mods**: a `[ShaderOverride]` acts by shader hash, so once this INI is loaded the hair outline colour pass of other RabbitFX-style characters no longer receives RabbitFX textures either (the black lines disappear, and the outline colour comes from the game's original hair texture, as with slot style). ## Fix of the probe's region hash cache (T-010, afternoon of 2026-10-07, probe 0.1.4)

- The user asked for the "suspected probe problem" noted at the end of the previous section to be dealt with. **Reproduced in the sandbox, fixed, installed, and loaded by the restarted game.**
- Cause: `g_rcache` in `capture.cpp` is keyed by `{buffer address, offset, size}` and uses the write count (epoch) and `gen` to judge whether an entry is still valid. After a buffer is destroyed, the registration is simply replaced when a new buffer gets the same address, and the write count goes back to the initial value 1; if the old buffer was never written either (which is exactly the case for mod buffers created with initial data), `hist_intact` judges "unchanged", and the hash of the old buffer is given to the new one. The cache is not emptied while the client stays connected, so "change a mod → reload → look at the hash" hits it squarely.
- Reproduction: the sandbox program got `--recreate-mesh3 N` (every N frames it destroys the three buffers of mesh 3 and re-creates them with the original size and different content); `selftest.py` got a group of checks that compare, every time, the recorded region hash with the CRC of the bytes read back. 0.1.3: 114 of 180 comparisons do not match (and there really is address reuse); 0.1.4: three runs of 180 each all match.

`0.1.1` separates installing device hooks from choosing the capture target. The first swap chain found determines, through `GetDevice` / `GetImmediateContext`, the device/context it belongs to and holds them; an auxiliary device no longer overrides the target. The `context1` capability is stored per context, and the GPU writer is limited to the selected context and the swap chain that was found. The status gained the target pointers and the draw count of the selected context, and an empty capture gives a warning.

Once a target is chosen, a replacement swap chain of another device is not accepted, and the log says to restart; deciding automatically which of several swap chains is the main picture is not supported yet. The integrity of captures across the destruction/re-creation of a swap chain on the same device is not verified; see the known issues.

Live mode got a generation at the same time: after a stop (`enable=false`) or a disconnect, in-flight frames of the old session cannot be back-filled into the summaries; re-configuring parameters with `enable=true` does not change the generation.
